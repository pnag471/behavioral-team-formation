# Research Traceability Matrix

Companion to [`research_alignment_audit.md`](research_alignment_audit.md). Every row cites exact
files/functions/lines as of commit `f800b4f` (branch `feat/gemini-integration`). "Evidence" points to
either production code or to an executed test/harness result in
[`research_alignment_results.json`](research_alignment_results.json).

**Source-of-research-claims caveat:** `docs/research-notes.md` exists but is **empty** — the repository
has no literature-review file. The only research citations in the codebase live as inline comments in
[`backend/traits/rubric_v1.yaml`](backend/traits/rubric_v1.yaml) (Peeters et al. 2006; Bell 2007; Ohland
et al. 2012; Loughry et al. 2007; De Dreu & Weingart 2003; Jehn 1995). Those are cited below where the
implementation itself cites them. Everywhere else, "research criterion" reflects the working-hypothesis
definition supplied in this audit's brief, not a codebase-internal citation — flagged in the
"Fully/Partially/Not supported" column as `(no in-repo citation)`.

## Status update — Part 6 (this session)

The table above is preserved UNCHANGED as the audit-time (Part 1) snapshot — do not read it as
current. Rows 2a/2b (ability), 5 (familiarity), 7 (individual utility/fairness), and 8
(preference/stability) described genuine "Not supported" gaps at that time; all four now have real
implementations (Parts 2–5.6), and Part 6 (this session) integrates all seven criteria into one
configurable framework rather than leaving each as an independent, uncoordinated addition:

| # | Row | Current status | Where |
|---|---|---|---|
| 2a/2b | Mixed ability | **Partial, opt-in** — `CompetenceSignature.ability_score` ([0,1] scale, falls back to `experience_level`), `compute_ability_metrics()` always reported, `_ability_balance_improve()` optimizes only when `ability.enabled=true` (now reachable via the `research_balanced` profile). Still an explicitly documented HYPOTHESIS, never promoted to a hard constraint — see `AbilityConfig`'s docstring and `app.matching.CRITERION_REGISTRY`. |
| 5 | Familiarity / anti-clique | **Partial, opt-in** — real `familiarity` DB table (`FamiliarityEdge`), `compute_familiarity_metrics()` always reported (team-induced `connected_familiarity_cluster`, coverage-aware `insufficient_data` handling), `_familiarity_balance_improve()` optimizes only when `familiarity.enabled=true`. |
| 7 | Fair individual benefit | **Partial, opt-in** — real per-student `StudentUtility` (skill/behavioral/availability/interest fit), `compute_assignment_utilities()` always reported (min/mean/variance, exact worst-case regret below a roster-size cap), `_fairness_improve()` optimizes only when `fairness.enabled=true` (now reachable directly or via `fairness_priority`). |
| 8 | Preference & stability | **Partial, opt-in** — real `preferences` DB table (`PreferenceEntry`: ranked/tied/avoid/characteristic), tier-scored `compute_preference_metrics()`, THREE formal stability definitions (`compute_stability_metrics`: blocking pair / blocking swap / beneficial feasible move — see Part 5.5's terminology correction), `_preference_repair_improve()` + `_hard_avoidance_repair()` (avoidance is a genuine hard constraint independent of `preference.enabled`) reachable via `preference_priority`. |

**What changed structurally in Part 6, not just per-criterion:** a centralized
`app.matching.CRITERION_REGISTRY` now classifies every criterion (hard constraint / soft objective /
evaluation-only / optional post-processing) in one place rather than each part's own scattered
docstrings being the only source of truth; a named-profile system (`legacy` /
`research_balanced` / `fairness_priority` / `skill_priority` / `preference_priority`, see
`docs/optimization_profiles.md`) replaces "an instructor must know to flip five independent flags" with
one documented, resolvable choice; and a normalized cross-criterion objective report
(`compute_normalized_objective`) lets all seven criteria be compared on one `[0,1]` scale for the first
time, with an explicit overlap check (Section 4 of the Part 6 spec) confirming no two components
double-count the same underlying signal.

**What did NOT change:** the `legacy` profile (the default — an existing client that omits `profile`
receives this) reproduces every row's PRIOR-part behavior exactly; no research hypothesis was promoted
to a hard constraint; row 9 (explanation quality) and row 10 (scoring determinism) are unaffected by
Part 6 (`explanation_quality` is explicitly classified `optional_post_processing` in the registry, never
part of formation). See `research_alignment_audit.md`'s Part 6 update for the full accounting, including
the empirical profile comparison and remaining performance limitations.
